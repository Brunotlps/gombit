# Canonical benchmark schema

Issue [#141](https://github.com/gombit-dev/gombit/issues/141) §"Canonical
realistic application" requires every implementation under `benchmarks/apps/`
to converge on the same PostgreSQL schema — same tables, same columns, same
indexes, same semantics — even though each framework expresses it through its
own migration mechanism (Atlas for Gombit, GORM `AutoMigrate` for the Gin+GORM
control, Django/Rails/Laravel/NestJS ORMs for the ecosystem-context apps).
This document is the reference every implementation's migration is checked
against; it is not itself a migration.

## Tables

```sql
CREATE TABLE users (
    id         BIGSERIAL PRIMARY KEY,
    email      TEXT NOT NULL,
    name       TEXT NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE UNIQUE INDEX users_email_key ON users (email);

CREATE TABLE projects (
    id          BIGSERIAL PRIMARY KEY,
    owner_id    BIGINT NOT NULL REFERENCES users (id),
    name        TEXT NOT NULL,
    description TEXT NOT NULL DEFAULT '',
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX projects_owner_id_idx ON projects (owner_id);
CREATE INDEX projects_created_at_idx ON projects (created_at);
```

This matches issue #141 §3 exactly: `users.email UNIQUE`,
`projects.owner_id`, and `projects.created_at` are the three required
indexes; `projects.owner_id` is also a foreign key to `users.id` so the list
endpoint's owner preload (§"Canonical list query") is a real join, not an
implementation convenience.

`BIGSERIAL`/auto-increment integer IDs, not UUIDs, to match this repo's own
GORM convention (`gorm.Model.ID uint`, see `database/conformance/models`) and
keep deterministic seed ordering simple (issue §"Canonical list query"
requires "the same ordered IDs for a known query").

**What "equivalent" means in practice** (verified against `benchmarks/apps/gin-gorm`,
the first implementation, via `psql \d`): index and constraint *names* are
whatever the ORM's migration tool generates (GORM named the unique index
`idx_users_email`, not `users_email_key` as illustrated above) — only the
columns, nullability, uniqueness, and FK target need to match, not the
identifier strings. Likewise `DEFAULT now()` above is one valid way to
guarantee a `NOT NULL` timestamp; an ORM that populates timestamps at the
application layer on every write instead of via a DB-level default (GORM's
default behavior for `CreatedAt`/`UpdatedAt`-named fields) satisfies the same
contract without one — `gin-gorm`'s columns are `NOT NULL` with no DB
default, verified column-by-column against this table.

## Canonical CRUD API

Every implementation under `benchmarks/apps/` exposes:

```http
GET    /api/projects/{id}
GET    /api/projects?page=1&limit=20
POST   /api/projects
PATCH  /api/projects/{id}
DELETE /api/projects/{id}
```

- Success responses use Gombit's D10 envelope: `{"data": ...}` for single
  resources, `{"data": [...], "meta": {"page":, "limit":, "total":}}` for the
  list endpoint. **All apps use this shape, including the Gin+GORM control**
  — per issue #141 ("Responses should use Gombit's existing
  response-envelope convention so serialization work is comparable"), the
  envelope is held constant across this comparison so the measured delta is
  the framework/validation/routing cost, not a response-shape choice. This is
  a different call than `benchmarks/micro/scenario`'s framework-tax matrix,
  which deliberately let each stack use its own idiomatic default —
  intentional: that matrix isolates per-layer cost; this one isolates
  adopting-Gombit cost against a fixed contract.
- The list endpoint (`GET /api/projects`) returns 20 projects per page by
  default, ordered by `id DESC` (deterministic — issue §"Canonical list
  query" requires "deterministic ordering" and "the same ordered IDs for a
  known query"), with the owner relationship preloaded in the same query set
  (no N+1: one query for the page of projects, one query for their distinct
  owners, not one owner query per project).
- Every implementation serializes the same project fields:
  `id, owner_id, owner_name, name, description, created_at, updated_at`
  (`owner_name` is the preloaded relationship's payload — its presence in
  every response is what the N+1 check is actually verifying).

## Seed dataset

Deterministic: 1,000 users, 100,000 projects (issue's recommended initial
size), generated by a single reproducible command, never inside a timed
benchmark run. Users seed as `user-0001@example.com` .. `user-1000@example.com`
(deterministic emails so `users.email UNIQUE` is exercised and every
implementation seeds identical rows); projects distribute round-robin across
users so every user owns ~100 projects, with deterministic
`name`/`description` derived from the project's own sequence number so two
implementations' seeded row N is byte-identical.

## Adding a new implementation

1. Express the tables/indexes above through the framework's own migration
   mechanism (Atlas `migrate diff`, GORM `AutoMigrate`, a Django/Rails/etc.
   migration).
2. Implement the five routes against that schema, envelope, and pagination
   shape.
3. Point the implementation at the same seed data (`benchmarks/apps/*/seed`
   — one seeder per implementation, same target row counts and content).
4. Run the fairness checks (`benchmarks/apps/*_test.go` /
   `make benchmark-crud`, once wired) before trusting any performance number
   from it.
